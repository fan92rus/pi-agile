# agile-solve — спринтовый движок в формате workflow-скрипта

Порт pi-agile (расширение) в **один workflow-скрипт**. Цикл держит родительский скрипт,
каждый ребёнок await'ится — события не теряются, финальный receipt несёт весь след.
Суждение перенесено в детей (паттерн ledger-loop-mem).

## Когда применять

| Ситуация | Инструмент |
|----------|-----------|
| Кампания: много разнородных задач по репо, автодискавери, спринты | **agile-solve** |
| Одна церемония: диагноз → фикс под гейт | ledger-solve |
| Один точечный фикс без гейта | обычный worker-субагент |

**Предпосылки:** чистый git-worktree (script workers делают `git checkout -b`), `testCommand`
обязателен (нет гейта — нет делегирования), pi-subagents активен.

## Запуск

```
subagent({
  workflow: "C:/Users/user/.agents/skills/agile-solve/workflows/agile-loop.js",
  cwd: "<repo>", async: true,
  timeoutMs: <2-3× worst case; спринт ≈ 30-90 мин, кампания 3 спринтов ≥ 4-6ч>,
  args: { description, testCommand, taskSource: "bd-epic", bdEpic,
          bdTasks: <снимок листьев - скипает стартовый boundary>, doneWhen: "bd-epic-closed",
          sprintTasks?, maxSprints?, maxParallel?, mergeApproval?,
          workModels?, reviewModels?, modelLadder?, constraints?, bundleScript? }
})
```

Не совмещать `workflow` с `task` (хост отклоняет); полный контракт аргументов — таблица ниже.

### L0-бриф репо (`project-brief.md`)

Бандл ищет `.agents/project-brief.md` → `PROJECT-BRIEF.md` → `docs/PROJECT-BRIEF.md` и
показывает до 6KB в секции PROJECT BRIEF; отсутствие видно в выводе бандла (скрипт сам
подсказывает). Репо, в котором планируются кампании, должно нести бриф. Бриф заводится
**ОТДЕЛЬНОЙ задачей оркестратора** — воркер на своём шаге 0 бриф НЕ создаёт (scope
discipline: мета-работа вместо задачи). Минимальный шаблон:

```markdown
# Project brief (L0) — <repo>
Updated: <дата> (проверил: <кто>)
## Commands
- tests: `...` (timeout 300s)
- build: `...` (timeout 180s)
- lint: `...` (timeout 120s)
## Env gotchas
- <напр.: .sh/.githooks — только LF; workflow после правок верифицировать vm.Script;
  bd владеет core.hooksPath>
## Do not touch
- <пути вне задачи: .beads/issues.jsonl, чужие незакоммиченные правки>
```

## Федерация с goal-x: большие bd-деревья (taskSource=bd-epic)

Для деревьев уровня «5-8 эпиков × десятки задач» (пример: wt-swiftsnow, 16 этапов / 67 листьев / 216
зависимостей) слои делятся так: **L1 bd** — истина по дереву/зависимостям/росту; **L3 agile-solve** —
исполнитель ОДНОГО этапа (волны, ревью-цепочки, merge-дисциплина); **L5 goal-x** — драйвер кампании
(персистентность между рестартами, auto-continue, evidence, аудитор). Единица agile — ЭТАП, не дерево:
250+ детей цели упираются в fan-out 256 и бюджет запуска, а этап из 5-17 листьев (~20-90 детей)
комфортен. Драйвер для каждого этапа запускает один agile-прогон с `taskSource:"bd-epic"`, снимком
`bdTasks` и `doneWhen`; рост дерева по ходу работ подхватывается bd-cursor'ом на границе спринтов;
bd закрывает ТОЛЬКО драйвер — воркеры и workflow bd не пишут. Закрывая эпик, драйвер зеркалит краткую сводку кампании в комментарий закрытия: `result.analytics.summaryLine` из receipt'а workflow'а (wall, дети, токены, классы отказов; ретро целиком — `.agile-js/<runid>/retro-<runid>.md`).

## Матрица ускорения (ИССЛЕДОВАНИЕ — не контракт; реализовано только помеченное ✓)

| Механизм | Экономит | Когда можно | Статус |
|---|---|---|---|
| discovery + curator дети | 2 ребёнка/спринт + их токены | задачи уже специфицированы в bd (taskSource=bd-epic) | ✓ реализовано |
| retro ребёнок | 1 ребёнок/спринт | стоп-решение детерминировано (doneWhen/maxSprints/budget) | ✓ реализовано в bd-epic |
| arbiter | судья споров | уже только при разногласии review/rework | ✓ было изначально |
| SDD фаза 0 | 1 ребёнок + время | `sdd:false` — в bd-режиме выключена принудительно | ✓ было/✓ в bd-epic |
| review-ребёнок по тиру (none/lite/full — см. «Тиры ревью») | 1 ребёнок + независимый прогон на задачу | тиражировать по полю задачи из bd (`review`); ПОЛНЫЙ merge-гейт НЕ отменяется никогда | ✓ реализовано (поле `review` задачи; вне {full,lite,none} деградирует вверх до full) |
| условный финализатор | 1 ребёнок/кампанию | отчёт уже полон (status completed, counts полны) | ✗ исследование |
| параллельные ЭТАПЫ на уровне драйвера | стен-время кампании | непересекающиеся поля файлов двух эпиков | ✗ уровень L5 |

НЕ выкидывается никогда: merge-гейт с полным suite, head-binding (verdict по SHA), acceptance-evidence в structured output (schema-канал, см. «Отчётный контракт»),
кросс-модельность ревью на полном тире, bd как источник истины.

**Деградация single-model (реализована):** если доступна только одна модель (work и review совпадают либо список из одного), кампания не падает: префлайт пишет warn в лог, ревью идёт на этой же модели (кросс-модельность не выполняется). Кросс-модельность ревью — дефолт при ≥2 доступных моделях. Если trip оставил ревьюеру только модель автора, берётся она же + warn `cross-model degraded`.

## SDD task-engine (включён по умолчанию)

Перед спринтами кампания запускает **фазу 0 — sdd-setup** (один child на профиле `sdd-worker`, inheritSkills: true):

- **Автоклассификация**: фичи / новое поведение / неустоявшийся дизайн → setup проходит цепочку sdd-idea → prd → spec → tasks (вопросы сам решает — согласование делегировано, решения в Gate Log, гейты `.status`), артефакты в `<sddDir>/specs/<slug>/`, коммит в main. Пакет известных багфиксов / чистка / рутина → `mode=skip` с обоснованием в журнале — кампания идёт по-старому.
- **Куратор читает из tasks.md**: незакрытые пункты по порядку; `acceptance` = критерии из спеки дословно; у задачи поле `sdd_item` — строка чекбокса дословно. Волны и `engine` (bare/ledger) — как обычно: **SDD определяет ЧТО, движок — КАК**.
- **Write-back**: мерджер после squash ставит `[x]` своему пункту в tasks.md и коммитит `sdd: done ...`. Все пункты закрыты → куратор вернёт пустой план → `stopReason: "sdd tasks exhausted"`.
- **Resume**: артефакты уже есть → setup валидирует `.status` и ничего не пересоздаёт.
- **Override**: `sdd: true` (форс артефакты), `sdd: false` (легаси), `sddDir` — свой каталог.
- **Per-task движок `sdd`** — отдельная вещь: фича ВНУТРИ рутинной кампании может быть классифицирована куратором как `engine: sdd` — воркер на профиле sdd-worker сначала делает компактную SDD-цепочку на своей ветке, потом код; доступен и без фазы 0.
- В receipt: `sdd: {active, tasksFile}`. Сбой setup (инфра) → кампания продолжается без SDD-движка, деградация честная (запись в журнале).

## Ретраи инфраструктуры (встроено)

Бэкенд модели может флапнуть или перезапуститься посреди кампании. `runChild` классифицирует сбои: **потеря structured output — «schema-missing», БЕЗ ретрая** (ребёнок уже мог занести работу — повторный бриф рискнёт переimplementировать её); **перегрузка/429 — следующая попытка на следующей модели из `args.modelLadder`** (счётчик попыток общий; review/arbiter никогда не сходят на модель работы — кросс-модельность; лестница исчерпана — «retry-needed», в чекпоинте `wait.lastModel` несёт последнюю модель; дефолт лестницы пуст = прежний fail-fast, таймеров в песочнице нет — шторм мгновенных попыток бесполезен); **транзиентный транспорт** (connection refused/reset, 502/503/504, engine crash) — ограниченное число повторов (`maxRetryAttempts`, default 6; `args.retryDelays` работают только там, где есть таймер — в тестах; в песочнице задержка 0). Красный гейт, честный отказ, таймауты не ретраятся — их ловят штатные catch-цепочки (деградация/abort). Ретрай-ключи: `key~retry2`, `key~retry3`, … (отдельное пространство имён — не пересекается с ключами review-раундов)
Сна нет: `Atomics.wait` удалён (блокировал весь однопоточный workflow), `setTimeout` в песочнице pi-subagents отсутствует (проверено рантайм-смоуком) — retry в песочнице мгновенный и ограниченный, пауза возможна только на уровне выше (resume кампании).
- **Трекер запусков:** промис `runs.run` обязан стоять в ГОЛОВЕ цепочки
  (`runs.run(...).then(ok, fail)` — валидно). Обёртка `Promise.resolve().then(() => runs.run(...))`
  не оставляет прямой регистрации на промисе запуска → pi считает запуск «unawaited»,
  весь воркфлоу получает терминальный failed ПОСЛЕ того, как вся работа сделана,
  и return-значение скрипта теряется

## Параллелизм (волны куратора)

- Куратор при планировании присваивает каждой задаче `wave` (целое ≥ 1) — это ЕГО решение, с уклоном «параллелить по умолчанию»: одну волну получают любые СЕМАНТИЧЕСКИ независимые задачи (ни одна не строит на изменении другой) — частичное пересечение файлов допустимо: текстовые конфликты на squash разрешает мерджер, гейт ловит семантику; разные волны — только для реальных зависимостей (исполнение по возрастанию номеров; номер волны = уровень зависимости, задач в волне может быть больше maxParallel — пул сам прокрутит их через дорожки и не ждёт самую долгую). Для широкой волны (профиль wide-stage) и для bd-листьев допуск пересечения сужен: пересечение файлов = цепочка deps (см. «Правило декомпозиции»).
- Задачи одной волны: work-дети запускаются ОДНОВРЕМЕННО, каждый в своём git worktree (`git worktree add ../wt-t<N>-<slug> -b <branch>`, затем `npm ci` внутри — в чистом worktree нет node_modules). Основная рабочая копия не трогается.
- После settle'а волны: review → rework → merge для каждой задачи ПОСЛЕДОВАТЕЛЬНО (main — общий ресурс; ревью лёгкие). Merger обязан ПЕРЕД мержем ребейзить ветку на актуальный master: конфликты решаются на rebase с сохранением обоих намерений (читает диффы соседних веток волны), после успешного rebase мерж идёт без конфликтов (squash/ff) — пересечение файлов не повод сериализовать. Merger попутно делает `git worktree remove`.
- Relay-режим (гибрид): церемония запускается с cwd = worktree, ledgerDir — абсолютный путь в ОСНОВНОМ дереве (`git worktree list`), поэтому её стейт переживёт работу.
- Реалистичный потолок: maxParallel 2-3 — дети делят один стенд LLM и CPU на тесты; гейт 900с это переживает, но стенка растёт нелинейно. Ширину 4 слота даёт только профиль wide-stage ниже.
- Claim-dirt (`.beads/issues.jsonl`): pre-flight — промпт-контракт, а НЕ механическая проверка движка: правило `claimDirtRule` в брифах merger/drop-ребёнка требует закоммитить единственную bd-грязь path-scoped `git add`+`git commit` БЕЗ `|| true`, затем проверить чистый `git status --porcelain` по этому пути; провал команды — явный отказ (`merged=false`/`dropped=false`, причина в note), любая другая грязь — отказ; движок исполнение git-команд ребёнком не перепроверяет — контракт закреплён тестами текста правила во всех семьях брифов (`agile-loop.test.mjs`).

## Wide-stage профиль (широкая стадия)

**Статус: активен** (в коде: `maxParallel` кап 4, `maxPerModel` 1..8; контракт параллельной пары покрыт тестами `paired wave` и `merger pre-flight under parallelism` в `agile-loop.test.mjs`). Параллельная пара disjoint-листьев безопасна: work-ребёнок запускается с `acceptance:false` (хост не снимает staged-снимок main при запуске), `noStagedFiles` проверяется по его собственному worktree, а сиблинг-мерж, пришедший во время его жизни, ему не мешает. Все мержи идут через `mergeChain` — на main в каждый момент живёт один merger-ребёнок, и его pre-flight видит main без параллельных писателей от движка (bd-экспорт claim-dirt остаётся под `claimDirtRule`).

Применяется, когда стадия содержит **≥ 4 независимых листа** с непересекающимися полями файлов (правило декомпозиции ниже):

| Арг | Значение | Смысл |
|---|---|---|
| `maxParallel` | `4` (допустимо `3`) | рабочий пул и post-очередь (postSlots = maxParallel) держат до 4 задач одновременно |
| `maxPerModel` | `2` | живых детей на модель не больше 2 — параллелизм не штормует квоту одной модели |

**Трейдофф:** квоты моделей горят быстрее, стенд LLM и CPU делят 4 задачи. При 429 в журнале откатывайся на `maxParallel: 3`, затем `2`. Для стадии с < 4 листьями профиль не нужен: дефолт `maxParallel: 3` уже покрывает.

**sprintTasks для волны:** `sprintTasks` = числу листьев в волне (2–4 типично, кап 12); `maxParallel` не меньше числа листьев волны и не больше 4 (дефолт 3 покрывает пару и тройку; четвёртый слот — только wide-stage). Листья с общим файлом МОЖНО ставить в одну волну: merger ребейзит ветку на актуальный master — конфликты решаются на rebase, после него мерж без конфликтов; страховка — полный сьют; disjoint-поля предпочтительны как ноль конфликтов (см. правило декомпозиции).

## Правило декомпозиции (листья под параллелизм)

Применяется при разбиении работы на листья (bd-эпик или план широкой волны куратора). Поля файлов листа — `files_hint` в снимке `bdTasks` (или ПОЛЕ в описании листа):

1. **Листья с непересекающимися полями файлов** и семантически независимые → одна широкая волна, параллельно; ноль конфликтов на мерже.
2. **Общий файл — предпочтение, не запрет:** disjoint-поля предпочитаются (ноль конфликтов), но параллельная волна с общим файлом допускается — merger ребейзит ветку на актуальный master, конфликты решаются на rebase (в контексте собственного диффа ветки), после успешного rebase мерж без конфликтов; полный сьют после сквоша страхует от semantic-поломки (ревью видит ветку на старой базе, композицию веток никто не ревьюит). Экономия wall реальна только если конфликтов нет; при конфликте цена (резолв на rebase/переделка листа) выше serial — серийная цепочка deps остаётся дефолтом для заведомо пересекающихся правок одной функции.
3. **Заголовок листа — часть контракта ревью:** re-scope обязан обновлять и заголовок, не только описание; протухший заголовок отклоняет годную работу по мета-причине (ys9/r1: 29 мин впустую). Контрактные метаданные (заголовок/files_hint/приёмка) сверяются до LLM-ревью дешёвым механическим пре-чеком — мета-отклонение не должно стоить rework-цикла.
3. Wide-stage профиль для волн с общим файлом — на усмотрение драйвера.
4. **Риск исполнения — отдельный лист, чистые части не ждут рискованные:** часть работы с недоказанным или архитектурным критерием (требует рантайм-примитива или нового механизма, которого в песочнице или гейте ещё нет; пример — таймер/пауза, см. «Ретраи инфраструктуры») оформляется ОТДЕЛЬНЫМ листом. Чистые части не получают `deps` на рискованный лист: они идут своей волной и мержатся, пока рискованный итерирует. Рискованный лист получает `deps` на чистые, только если реально строится на них. Заголовок каждого листа называет только свою часть (п.3). Прецедент `pf3`: лист из 3 частей — части (1) и (3) одобрены в раунде 0, но 3 rework'а части (2) с архитектурным критерием держали весь лист. Признак риска — не поле файлов: пересечения файлов решаются по п.2, риск — по этому пункту; дополняет «Ширину листа» (п.2 в «Постановке bd-листьев»).

## Постановка bd-листьев (контракт, не исследование)

1. **Текст bd-задачи = только домен:** acceptance-критерии, ограничения, поле файлов (`files_hint`). Формат отчёта учит движок через ACC_STRUCTURED-бриф (structured output = отчёт). В текстах задач ни одного упоминания формата отчёта, его полей и head-плейсхолдеров. Прецедент `agents-s9w.1`: поля отчёта из bd-текста конфликтовали с фенсом, rework упал на whitelist фенса.
2. **Ширина листа:** если лист затрагивает больше 3 самостоятельных поведений (schema + validator + wiring + briefs + docs), нарезай его серией узких под-листьев с `deps`. Полный refute-ревью широкого листа сходится за 2+ rework, узкого — за 0-1. Прецедент: `agents-s9w.1` (6 под-задач в одном листе) дал 2 rework (status-enum, text-only JSON fallback); узкий `agents-s9w.2` смержился с первого прохода.
3. **Ориентиры для быстрой навигации (если известны):** когда куратор знает символы целевого файла — строка В КОНЦЕ текста листа: «Ориентиры: doMerge (merger: collapse+rebase), cooling (cooldown)». Формат: ПЕРВОЕ СЛОВО каждой пары — точное имя символа (ключ поиска, не семантика), в скобках — зона/зачем; префикс «Ориентиры:» — конвенция, не парсер; не знаешь — строка не пишется. Воркер проверяет актуальность дёшево: `lean-ctx graph symbol <имя>` → file::symbol + строки + исходник (~50 токенов; пустой ответ → `lean-ctx graph build` один раз в своём cwd). Ориентиры — подсказка, не контракт; НОМЕРА СТРОК НЕ УКАЗЫВАТЬ (протухают при первом же мерже — имена символов стабильны).
4. **Требования понятны без переспроса:** каждый acceptance-пункт — проверяемое утверждение с наблюдаемым исходом (выход команды/гейта, наличие/отсутствие теста, детерминированное состояние репо), одно утверждение на пункт — воркер обязан уметь ответить done/not-done без толкования. Термины — из словаря репо: имена символов, файлов, полей (связка с «Ориентирами» п.3). Оценочные слова («быстро», «аккуратно», «как прежде») и непроверенные допущения о рантайме (примитив не существует — прецедент runs.host, pf3) запрещены: второе — не «сложный критерий», а рискованный лист (см. «Риск исполнения»). Клапан: два rework на ОДНОМ критерии — стоп, не итерировать механизм, переформулировать критерий у владельца (bd remember). Тот же стандарт обязателен и для ТЗ от ревьюера: пункты `fix_list` (fix-only rework) — это acceptance-контракт rework-воркера, один фикс на пункт, наблюдаемый исход, символы из словаря репо; расплывчатые глаголы («почини», «улучши», «поправь стиль») без проверки — то же отклонение, что мутный критерий куратора.

## Маркер PLANNED для параллельных док-vs-код листов

Когда в одной волне идут док-лист и код-лист одной фичи (поля файлов не пересекаются: док — `SKILL.md`, код — `workflows/*.js` и тесты):

- док-лист описывает фичу, которой в коде ещё нет, с маркером `ПЛАНИРУЕТСЯ - реализуется листом <id> (код), в коде пока НЕТ` (тот же формат, что в контракте args выше);
- маркер код-лист НЕ снимает: его поле не включает `SKILL.md`. Снятие маркера — отдельный док-лист с `deps` на код-лист (общий файл `SKILL.md` = цепочка по правилу выше);
- пока маркер стоит, фича не описывается в тексте как работающая.

## Тиры ревью (full / lite / none)

**Активен** (поле `review` задачи; значение вне {full,lite,none} деградирует ВВЕРХ до full; тир не указан → `full`).

| Тир | Для каких листьев | Что делает ревью-ребёнок |
|---|---|---|
| `none` | не-кодовые листья: документация, текст конфигов, test-only без логики | ревью-ребёнок НЕ запускается (0 ревью на лист); гейт в брифе и полный merge-гейт остаются, acceptance = structured output |
| `lite` | механика: переименования, переносы, однотипные правки | ревью по чек-листу diff, без refute-протокола |
| `full` | логика кода: алгоритмы, состояния, безопасность, публичные API и схемы | полное ревью как сейчас (refute-протокол, кросс-модельность) |

Инвариант для всех тиров: ПОЛНЫЙ merge-гейт, head-binding (verdict по SHA) и acceptance-поля structured output не отменяются. Лист без поля `review` ведётся как `full` до решения о дефолте.

## Отчётный контракт (acceptance = structured output, rp-schema)

У work/rework/report-repair/repair детей **structured output И ЕСТЬ acceptance-отчёт** — двойной ручной канал (фенс `\`\`\`acceptance_report` в финальном сообщении) устранён: schema-канал дал 0 отказов за ~100 живых детей, а ВСЕ salvage обеих кампаний случились на ручном фенсе; устранение дубликата устраняет класс отказов.

- **Запуск ребёнка:** `withGate` ставит `acceptance: false` (прецедент boundary/discovery-детей) — host не требует фенс и не парсит отчёт из финального сообщения. Верхнеуровневый `gate` НЕ используется: `normalizeGateAcceptance` превращает его обратно в verified-acceptance с обязательным фенсом. Гейт-команда НЕ исчезает: она остаётся в брифе («Verification command must pass before you finish»), воркер прогоняет её сам, а мерджер механически повторяет полный suite на main перед каждым коммитом.
- **WORK_SCHEMA несёт acceptance-поля** (все required): `head` — 40-hex SHA (`^[0-9a-f]{40}$|^$` — пустой только у verify-only листьев без коммитов), `testsAddedOrUpdated` — массив строк `<файл>: <N> cases` (`[]` ровно когда тестов нет), `commandsRun` — массив `{command, result: passed|failed|not-run, summary}` (минимум 1 запись), `validationOutput` — непустой массив решающих строк гейта, `residualRisks` — массив строк, `noStagedFiles` — const true, `criteriaSatisfied` — ровно две записи с id `criterion-1` (scope) и `criterion-2` (evidence), каждая `{id, status: "satisfied", evidence}` (status — ровно "satisfied", другие значения отклоняются).
- **`validateAccStructured(so, verifyOnly)`** — семантическая перепроверка отчёта в самом workflow (в `runChild` для каждого WORK_SCHEMA-ребёнка): нарушение любого поля = ошибка `schema-missing: <поле>` — salvage-класс: работа на ветке спасается report-repair ребёнком (восстановление отчёта из реального состояния ветки), бриф реализации никогда не перезапускается.
- **Финальное сообщение** — свободная сводка для вызывающего (маркер `FINAL REPORT:` в work-брифе остаётся); фенс эмитить НЕ нужно (случайный фенс безвреден — host его просто игнорирует).
- **`rec.head` = `so.head`** каждого schema-valid отчёта: ревьюер и мерджер всегда проверяют СВЕЖИЙ head последнего валидного отчёта (rework/salvage обновляют его) — класс отказов «branch head moved» убит конструированием.
- Мутационные пробы: у каждой проверки `validateAccStructured` есть свой designated тест в `agile-loop.test.mjs` (удаление проверки краснит свой пробник).

## Lifecycle

- **Пауза/крash:** состояние = журнал + git-ветки. Перезапуск с тем же `journalDir`
  (curator читает журнал, не повторяет сделанное); незакрытые ветки `agile/*` —
  точка входа восстановления
- **Порядок детей:** curator-режим: discovery → curator(approve) → спринты → retro; bd-epic: discovery/curator/retro НЕ запускаются — вместо них boundary-ребёнок (курсор-снимок + janitor + bd-close смёрженных). Внутри спринта на лист: work (свой worktree) → приёмка structuredOutput (провал формы → report-repair, 1 попытка) → review по тиру (только при принятой приёмке) → rework ≤ N с carry-over → arbiter → merge. Work-дети волны идут ПАРАЛЛЕЛЬНО (maxParallel 1–4, файл-непересекающиеся поля), слияния сериализует mergeChain; maxParallel=1 — легаси-последовательность
- **Провал main-чеков после merge:** merger сам делает `git reset --hard` и пишет
  `merge-failed` в журнал
- **Смерть ребёнка:** catch-ветки в скрипте; «arbiter-failed» оставляет ветку на ручной разбор

## Известные грабли

- **Pre-flight перед запуском (обязателен):** (1) smoke-генерация на стенде
  (`/v1/chat/completions` с реальным ответом — 200 в `/v1/models` ничего не доказывает);
  (2) `git status` в cwd чист; (3) `journalDir` вне индекса git — добавь в
  `.git/info/exclude` (иначе журнал уедет в воркерские коммиты); (4) в constraints
  воркерам: точный `git add <файлы>`, никогда `git add -A` (untracked-мусор репо уедет
  в ветку); (5) если тест-сьют репо сам мутирует tracked-файлы (напр. `.beads/`) —
  откатывай их в constraints
- Грязная рабочая копия на старте задачи → воркер честно стопится; чисти до запуска
- Нельзя параллелить воркеров в одном checkout — волна идёт через отдельные worktree (Wide-stage профиль); maxParallel=1 — легаси-режим без worktree
- `contact_supervisor` недоступен (resume-сценарии) → curator идёт с
  `approved_by_caller:false` — проверяй флаг в receipt
- Токены по детям — внешним анализатором (`metricsScript`, по умолчанию `analyze-campaign.mjs`; в receipts usage нет); финальная кампания запускает его сама (campaign-analytics, см. `metricsScript`) и кладёт metrics.json + retro в `<journalDir>/<runid>/`
- **Гейт-таймаут не теряет работу:** верификация `gate` наследует per-tool дедлайн
  (5m по умолчанию); тест-сьют 2м+ под нагрузкой не влезает. Скрипт ставит детям с
  гейтом `toolTimeoutMs: 600000`. Если всё же таймаут — коммит воркера уже на ветке,
  catch-цепочка ведёт его через reviewer как incomplete; НЕ добавляйте gate-timeout
  в ретраи — повторный воркер упрётся в грязную копию и честно стопнется
- **Git-хуки, стейдящие мусор в коммит:** напр. bd/beads hook реэкспортирует
  `.beads/issues.jsonl` при каждом commit. Воркеру после коммита проверять
  `git show --stat HEAD` = только свои файлы; при загрязнении: восстановить файл
  из базы (`git checkout <base> -- <file>`), `git add <file>`, `git commit --amend --no-edit`
- **Driver hot-edit файлового поля в полёте:** driver (L5) может править на master файл, который входит в поле ещё не смёрженных листьев кампании. Это допустимо: merger делает collapse → rebase на main → squash, и такой конфликт сводится на rebase-шаге (кейс 3c6f4b1: collapse-патч влит mid-flight, merger свёл конфликт). Но каждая такая правка — НАМЕРЕННАЯ инъекция конфликта во все живые ветки, которые трогают файл. Применяй точечно: одна правка на один файл, только при срочной потребности мастера (блокер кампании), не серией «заодно». После правки смотри merge-отказы и rework-атрибуцию в retro (`analyze-campaign.mjs`) — тот же эмпирический критерий, что у композиции по полю файлов («Правило декомпозиции», п.2); семантику ловит только полный сьют.
- **Воркер флэйлит на самописных скриптах:** симптомы — воркер в цикле edit-ошибок на
  собственном scratch-файле (debug-*.mjs / temp-file + node:fs скриптинг), счётчик токенов
  ушёл за 200k. Восстановление — steer с ОДНИМ конкретным предписанием: бросить скрипт,
  файл-поле, точные шаги, прогон тестов. Прецедент: воркер листа agents-5yr поднят
  стером после 252k токенов и дошёл до merged (bd: CLOSED, merge 6f6df75e). Профилактика:
  reuse-first в глобальном (runtime) брифе воркера + правило «NO SCRATCH DEBUG SCRIPTS»
  в брифах work/rework/repair движка (парный лист волны, cb5f529)

## Адаптивный выбор исполнителя (гибрид)

Движок выбирается **на каждую задачу**, а не на запуск. Решает куратор на sprint-plan (видно в запросе на одобрение, можно переопределить ответом):

| Задача | engine | Почему |
|---|---|---|
| Чёткий гейт + нетривиальная (мультисайт, алгоритм, интеграция, спека) | `ledger` | план-дисциплина + gate-цикл окупаются |
| Простая/механическая (даже с гейтом) | `bare` | церемония = 3-4× ради ничего |
| Без чёткого гейта (доки, research, UI-полировка) | `bare` | гейт вырождается в тривиально-зелёный; верификатор — reviewer |

Классификация ОБЯЗАТЕЛЬНА и по критериям, не по дефолту: у каждой задачи поле `engine_reason` с названным критерием (схема требует его наряду с engine); смешанный спринт — норма, а «всё bare» при наличии гейт-верифицируемой нетривиальности — дефект классификации (вызывающая сторона отклоняет план). Второй уровень — runtime: bare-задача исчерпала rework → арбитр предлагает вызывающей стороне `escalate-ledger`; ответ запускает ОДНУ repair-церемонию на существующей ветке (ledgerDir `ledger-ag-<slug>-fix`, церемонии велено продолжать, не перезапускать; затем обычный цикл review→merge; повторная эскалация запрещена). Безгейтовые задачи не эскалируются — церемонии не во что упираться. `escalateLedger:false` отключает. Обратное понижение ledger→bare не предусмотрено: к моменту очевидной простоты церемония уже оплачена.
