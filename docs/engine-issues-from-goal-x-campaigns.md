## ISSUE-1 (блокер): merge-шаг падает на «аналитических» листах с пустым диффом

### Факты

- bd-лист `gx-wb4.1` был investigation-only: единственный deliverable — отчёт
  `reports/gx-wb4/gx-wb4.1-root-cause.md`, а `reports/` в этом репо исключён из
  git через `.git/info/exclude` (bd stealth, прецедент E2–E4: reports никогда
  не коммитились).
- Воркер работу выполнил, ревьюер (run `ce2ab61f`, затем `3c128185` в спринте 2)
  независимо подтвердил корректность и **сам оформил диспозицию** «empty diff
  by design» в notes — вердикт ok.
- Merge-ребёнок на это взгляда не имеет: он выполняет `git commit -m …`, получает
  exit 1 (нечего коммитить) и честно репортит `merged=false` c «CLI exited 1»
  (прогоны `c358274e`, `47314fcb`, `f6cc6d15`).
- Итог: **3 спринта подряд на одном и том же листе с одним и тем же исходом**,
  кампания завершилась `stopReason: max-sprints reached`, `merged: 0`, хотя
  содержательная работа была готова уже после первого спринта. Лист в итоге
  закрывался оркестратором вручную.

### Механика

Merge-шаг движка безусловно требует коммит в ветке листа. Не существует
диспозиции «deliverable не является кодом» и способа провести merge без коммита.
Ревью-слой гибче merge-слоя: ревьюер умеет вербализовать «пустой дифф — by
design», merge — нет.

### Воздействие

- Полный слив лимита спринтов на задачах без кода (документация, расследования,
  конфиги в игнорируемых путях).
- Токены и время: 3 воркера + 3 ревью + 3 merge-ребёнка впустую (~2 часа стены).

### Направление фикса (предложения, выбери/совмести)

1. **Empty-diff disposition:** если (а) diff ветки против базы пуст, (б) вердикт
   ревью ok, (в) в отчёте ревью/воркера есть явная диспозиция о некодовом
   deliverable — считать задачу merged с пометкой `no-code`, закрывать bd-лист
   обычным порядком.
2. **Флаг на листе:** позволить bd-acceptance/задаче объявить
   `deliverable: analysis` (парсинг из текста acceptance или отдельное поле) —
   тогда merge-шаг пропускает коммит/merge и ограничивается проверкой вердикта.
3. **Escalation по структурному фейлу** (см. ISSUE-3): повторяющийся
   идентичный merge-фейл должен подниматься супервизору, а не съедать спринты.

### Критерий приёмки

- Кампания с листом «расследование + отчёт в игнорируемом пути» завершается
  `epic-closed` за 1 спринт, лист закрыт, в финальном return зафиксирована
  диспозиция `no-code merged`.
- Регресс-тест: пустая ветка + ok-вердикт → merged (не `merge-failed`).

## ISSUE-2 (дёрг, повторяется в каждой кампании): bd export-commit против stealth-bd

### Факты

- Финальный шаг `final-bd-close` (run `886ea352`) выполняет `bd export` и
  `git add .beads/issues.jsonl`. В pi-goal-x `.beads/` исключён через
  `.git/info/exclude` (bd init --stealth) → git отказывает, `git commit` не
  выполняется, шаг репортит `closed: false` с честным объяснением и вопросом
  «нужно ли форсить».
- Владельцем ранее ратифицировано: **bd export остаётся незакоммиченным
  (stealth by design)**, шаг export-commit в этом репо пропускается с пометкой
  closed-by-design. Движку эта ратификация неизвестна — каждый раз заново.

### Механика

Шаг export-commit безусловен; нет repo-уровневой конфигурации «bd работает в
stealth, экспорт не коммитим».

### Направление фикса

- Детект: если `.beads/` присутствует в `.git/info/exclude` (или
  `.beads/.gitignore`-подобный признак stealth-инициализации) → пропустить
  export-commit, репортить `"export": "closed-by-design (bd stealth)"`, не
  считать это фейлом кампании.
- Альтернатива/дополнение: явный флаг в args кампании (`bdExportCommit: false`)
  + автодетект как дефолт.

### Критерий приёмки

- В stealth-репо шаг export не выполняет git-операций и не попадает в счётчик
  failures; в обычном репо поведение прежнее.

## ISSUE-3: повторяющийся идентичный фейл не эскалируется, а жжёт спринты

### Факты

В кампании `d692acd3` три спринта подряд завершались одним и тем же исходом на
одном и том же листе (merge-failed, «CLI exited 1»), `retries: 0`, `failed: 3` —
и ни на каком шаге движок не поднял вопрос супервизору: «merge падает три раза
идентично — структурная проблема, нужна ручная интеграция?».

### Механика

Carry-механика переносит неудачный лист в следующий спринт без анализа класса
отказа. Нет fingerprinting'а отказов (лист + стадия + текст ошибки) и порога
эскалации.

### Направление фикса

- Считать класс отказа (стадия: work/review/merge; сигнатура ошибки).
- Правило: 2 одинаковых класса подряд на одном листе → приостановить лист и
  задать вопрос супервизору (supervisor request) вместо третьего спринта.
- В финальном return — сводка классов отказов (сейчас есть только в
  campaign-analytics постфактум).

### Критерий приёмки

- Искусственный сценарий «merge всегда падает с одной ошибкой»: кампания
  эскалирует после 2-го повтора, не расходуя maxSprints.

## ISSUE-4 (повторяющийся класс): ревью-ребёнок падает «Missing structured_output call»

### Факты

В E6 (`43f2bd82`) ребёнок `s1-t1-review` упал с `Missing structured_output
call`; движок сам восстановился через rework + свежий review-r1, merge
состоялся. Класс повторяется между кампаниями и стоит полный цикл rework
вместо дешёвого повтора.

### Направление фикса

- Перед полным rework — одна дешёвая повторная попытка того же ревью-ребёнка с
  явным напоминанием «заверни вердикт в structured_output» (или
  schema-forcing, если API позволяет).
- Отдельно считать эти фейлы в analytics как `review-schema-miss`, чтобы не
  путать с содержательными провалами ревью.

### Критерий приёмки

- Инжектированный кейс «ревьюер без structured_output»: один повтор вместо
  rework-цепочки; счётчик класса виден в return.

## ISSUE-5 (воспроизводилось в E5): воркер правит main вместо своего ворктри

### Факты

Два воркера E5 выполняли относительные Edit/Write, которые резолвились в
основную рабочую копию, а не в их ворктри; правки приходилось откатывать
вручную. С тех пор — только «следить», защиты на уровне движка нет.

### Направление фикса

- Preflight/постчек движка: во время спринта периодически (и перед merge)
  проверять `git status --porcelain` основной копии; грязный main вне ожидаемых
  путей → стоп-воркеру + авто- revert известного набора файлов + запись в отчёт.
- Жёстче: передавать воркеру абсолютный cwd и запрещать (prompt + проверка)
  пути вне ворктри.

### Критерий приёмки

- Имитация «воркер пишет в ../main» → детект на постчеке, откат, задача не
  мержится с чужими правками.

## ISSUE-6: после `epic-closed` остаются хвосты оркестратора

### Факты

В E5 (`gx-gqf`), E6 (`gx-443`) и gx-wb4 движок завершался с `stopReason:
epic-closed`, но **сам эпик в bd оставался OPEN** — его закрывал оркестратор
вручную. В E5 дополнительно на main остался незатреканный `.agile-js/`.

### Механика

`doneWhen: bd-epic-closed` проверяет «все листья закрыты», но не выполняет
закрытие самого эпика и уборку артефактов.

### Направление фикса

- При `doneWhen: bd-epic-closed`: после закрытия последнего листа движок
  выполняет `bd close <эпик>` с резюме кампании (stopReason, merges, ревью).
- `.agile-js/` создавать внутри déjà исключаемого пути или чистить за собой;
  в финальном return перечислять оставленные файлы.

### Критерий приёмки

- После кампании `bd show <эпик>` → CLOSED без ручных действий; `git status`
  основной копии чист.

## ISSUE-7 (инфра, было найдено в E5-prep): среда воркера отравляет гейты

### Факты

Любой pi-воркер работает с `PI_SUBAGENT_CHILD=1`; переменные наследовались
тестами воркера, палитра-тест валился 0/12 → гейт `npm test` был массово
красным без единой реальной регрессии. Починено в pi-goal-x
(`scripts/test-adapter-hooks.mjs` стриппит `PI_SUBAGENT_CHILD` /
`PI_SUBAGENT_DEPTH`), но это заплатка в каждом клиентском репо.

### Направление фикса

- Движок знает, что спавнит детей: стрипнуть `PI_SUBAGENT_CHILD` /
  `PI_SUBAGENT_DEPTH` из окружения, передаваемого воркерам/ревьюерам, по
  умолчанию (opt-out флагом). Тогда ни один клиентский репо не должен
  герметизировать себя сам.

### Критерий приёмки

- Воркер с тестом «упасть, если PI_SUBAGENT_CHILD установлен» проходит гейт.
