# Amendment 2 — укороченные промпты и детерминированный отчёт (rev.3.2)

## Причина

Прогон `agile-leaf-pilot-mwxja318-d014a9`: воркер сделал изменение, но `verify` упал на 1 тесте из-за ошибки в его же новом тесте (ожидал `rework`/`repair` в одной кампании, хотя движок ведёт их по разным веткам). Попытка `resume` с фазы `verify` (`...-mwjr9x2-55218f`) и с override фазы `review-correctness` (`...-mw xjxfoh-b45b4b`) оба раза закончились `spawn ENAMETOOLONG`: промпты ревью и отчёта интерполировали полный diff и полный вывод `npm test`, и subprocess-спавн стал слишком длинным.

## Изменение

1. Промпты `review-correctness` и `review-guardrails` больше не включают `{steps.diff-full.output}` и `{steps.verify.output}`; ревьюеры читают два исходных файла своими инструментами `read`/`grep` в cwd клона. Поле `tests` теперь литерально `verified-by-script-phase`.
2. Скорер `contains fail 0` убран из `gate-correctness`: зелёность тестов по-прежнему детерминированно проверяет отдельный `gate-tests` на выводе `verify`.
3. Фаза `report` стала `script`-фазой: короткая `node -e` пишет `results.md` из `input` с интерполяциями. Большой промпт агента-документалиста устранён; отчёт по-прежнему существует до гейтов. Добавлена фаза `report-stub` (от `base`): она создаёт заготовку `results.md` до тестов и перезаписывается полным отчётом, поэтому файл существует при падении `verify`. Если падает сама фаза `base` (грязный клон), заготовка не создаётся — ограничение сужено до «после успешной проверки базы»; чистоту клона проверяет сама фаза `base` перед созданием заготовки.
4. `baseline-test` запускается после `report-stub`, поэтому заготовка отчёта гарантированно создана до тестов. В `dependsOn` обоих ревьюеров добавлен `base`, в `dependsOn` отчёта — `base` и `baseline-test`: каждая интерполяция `{steps.X}` теперь имеет явную зависимость. Упоминания `diff-stat`/`diff-full` в `dependsOn` — это рёбра графа, а не интерполяции в промптах; из самих промптов большие выходы убраны. Модели, инструменты и гейты-контракты не изменены; добавлена только фаза `report-stub`.

## Проверка

`taskflow verify` вывод дословно: `✅ No issues found.` (0 ошибок, 0 предупреждений). Ожидаемый эффект: фазы ревью стартуют без `ENAMETOOLONG`; при зелёном тесте граф доходит до `post`. `report` стоит после ревью, поэтому при их BLOCK `results.md` записан; при раннем падении `verify` ревью и отчёт недостижимы по графу, и ведущий пишет отчёт вручную из трассы — это честно фиксируется как ограничение пилота, а не скрывается.

Полные выводы остаются в `input` script-фазы `report`, но по контракту Taskflow `input` — это текст, подаваемый в stdin (`SKILL.md`, §Script phases: `input` — optional text piped to the command's stdin), а `run` — array-форма без интерполяций. Командная строка остаётся короткой, поэтому `ENAMETOOLONG` не воспроизводится. `gate-tests` — дополнительная страховка: сама script-фаза `verify` уже падает при ненулевом exit, так что `fail 0` не может скрыть красный прогон.
